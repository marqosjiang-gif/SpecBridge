# 提示词模板库

> SpecBridge 内置的五份全流程提示词模板，覆盖从项目搭建到里程碑拆解的完整规划链。
> 使用方式：从项目建设开始，依次完成用户故事与优先级、产品功能与页面结构、技术方案和开发里程碑的梳理。在支持本地文件操作的 AI 编程工具中打开项目目录，按顺序每次复制一份提示词发送给 AI，完成当前步骤的讨论、确认和文档保存后，再进入下一步。

## 01 项目建设提示词

````text
请先为我们接下来要开发的产品建立项目目录和基础协作规则，完成后再和我讨论产品。

先查看当前目录，保留已有内容，复用职责相同的文件。按照下面的结构整理项目：

```text
项目根目录/
├── README.md
├── AGENTS.md
├── docs/
│   ├── facts/
│   ├── Spec/
│   └── 工程规则.md
└── src/
    ├── .git/
    └── .gitignore
```

各部分按以下方式使用：

### 1. docs/facts：产品的唯一事实文档

这里保存经过我确认的产品信息，例如产品用途、用户角色、使用流程、功能和数据规则。按实际需要划分文档，每份文档负责一个明确主题。

同一项事实只在一个位置维护，其他文档通过链接引用，不重复保存另一份。事实变化时更新原责任文档；发现冲突时先指出具体内容，与我确认后再修改。AI 提出的建议和我已经确认的结论要明确区分。

产品事实文档根据后续讨论结果逐步建立，现在只记录已经明确的信息，不提前编造内容或创建空文档。

### 2. docs/Spec：每次开发的任务规格

每个版本或明确的开发任务，在开始实现前建立对应的 SPEC（需求规格说明书），写清目标、修改范围、预期行为、必要依赖和验收条件。

SPEC 引用相关产品事实，说明本次具体要做什么，避免复制整套产品设定。开发与测试使用同一份 SPEC，分别检查实现和验收结果。当前还没有确定开发任务，先建立目录。

### 3. docs/工程规则.md：工程规则的唯一正文

请把以下规则写入这个文件，后续相关文件引用这里：

- `main` 保持稳定。每项开发从确认的基线创建独立任务分支，在分支上开发和自检。
- 开发前先确认对应 SPEC；开发完成后交付明确的提交及自检结果，独立验收针对这份固定提交进行。
- 研发自检和独立验收分别记录。发现问题后修复，再检查受影响的部分；验收通过后，按我的授权合并回 `main`。
- 开发、自检、独立验收、Git 合并各自的职责要明确，具体由哪些人或 AI 会话执行，后续由我确定。
- 合并与上线分别处理，上线需要我明确确认。只记录实际完成的操作和检查结果，说明尚未验证的范围。
- 修改涉及产品事实、接口或数据规则时，更新对应责任文档。已经存在的代码和组件先检查是否可以复用，不顺便修改无关功能。
- 保留必要的交付和失败证据，完成后清理本次不再需要的临时文件、测试服务和进程；任务验证并合并后，再清理对应分支及工作树。

### 4. src：项目源码与独立 Git 仓库

`src/` 是应用源码的独立 Git 仓库。源码、依赖声明、锁文件、测试以及构建和运行所需文件都放在这个目录，内部结构根据之后确定的技术方案建立。当前先创建目录并初始化 Git，产品设计和技术选型留待后续讨论。

### 5. README.md 与 AGENTS.md：阅读入口

`README.md` 简要说明项目、目录用途和文档入口。产品信息引用对应事实文档，工程要求引用工程规则。

`AGENTS.md` 说明 AI 开始工作时应该读取哪些资料，并引用 `docs/工程规则.md`，避免在多个入口重复维护同一套规则。

### 6. Git 与远端仓库

在 `src/` 中初始化并管理 Git，主分支使用 `main`，`src/.git/` 由 Git 初始化生成。已有仓库先检查当前状态，保留已有提交和未提交内容。

在 `src/.gitignore` 中根据实际项目排除密码、密钥、真实用户数据、依赖缓存、构建结果和临时文件。

`docs/` 和根目录管理文件单独保存、备份；`src/` 的提交和远端同步只覆盖该仓库内的文件。

远端仓库地址使用我提供的真实地址，按我的授权配置和同步。地址尚未提供时，先完成本地准备，并在结果中列明需要补充的信息，不自行创建远端仓库或声称已经完成同步。

完成后请检查实际文件和引用是否正确，向我展示目录结构、已建立的规则，以及本地 Git 和远端连接的真实状态。随后暂停，等我继续讨论产品，不直接开始实现功能。
````

## 02 用户故事与优先级提示词

````text
请和我一起梳理这个产品的用户故事，讨论每条故事的 P0—P2 优先级，等我确认后写入产品事实文档。

以下路径均相对于项目根目录，`docs/` 与源码仓库 `src/` 同级。

### 1. 确认产品目标和用户角色

先读取根目录的 `AGENTS.md`，按其中的文档入口查阅与产品目标、用户角色和用户故事有关的事实文档。

简要说明当前产品的核心目标和已经确认的用户角色，沿用已有结论。信息不足时，先围绕缺少的目标或角色向我提问，等我回答后继续。新增角色作为建议，由我决定是否纳入本轮讨论。

### 2. 按角色梳理用户故事

每轮围绕一个角色或一组相关故事展开，站在使用者的角度，说明他在什么场景下想完成什么、经历哪些关键操作，以及怎样算完成。

结合产品目标提出故事候选，让我补充、调整、合并或删减。每条故事使用稳定编号，例如 `US-001`；已有编号保持不变，新增故事接续编号。我确认当前角色的主要故事后，再继续其他角色。

### 3. 一起讨论优先级

故事梳理后，先和我确认本轮优先实现的范围，再按下面的含义讨论优先级：

| 等级 | 判断依据 |
| --- | --- |
| P0 | 当前版本必须满足，缺少它会使产品核心目标或主要使用流程无法成立 |
| P1 | 能明显改善主要使用体验，但缺少它仍能完成核心流程 |
| P2 | 改善细节或满足较少使用的场景，当前阶段可以推后 |

对每条故事给出建议等级和具体理由，说明缺少它的影响，以及它是否是其他核心故事的前提，邀请我判断和调整。

意见不明确时，用具体使用场景帮助我比较取舍。多个故事都被列为 P0 时，和我检查哪些故事是当前核心流程真正需要的。信息不足的故事先标记"待确认"，围绕缺口继续讨论。

### 4. 确认清单并写入事实文档

汇总本轮结果供我确认：

| 编号 | 角色 | 用户故事 | 优先级 | 判断理由 |
| --- | --- | --- | --- | --- |

用户故事应包含前面讨论清楚的场景、目标、关键过程和完成结果。单独列出仍待决定的问题，等我明确确认本轮清单及优先级后再写入。

写入时，先检查 `docs/facts/` 中是否已有负责用户故事的文档：已有则更新原文件；没有则创建 `docs/facts/user-stories.md`。保存我确认的故事、等级和理由，保留已有编号及本轮范围外的内容。相关产品定义引用原责任文档。

完成后回读文件，逐条核对故事、角色、优先级和理由与确认结果一致，向我说明文件路径和本轮确认的范围，然后等待下一步指令。
````

## 03 产品功能与页面结构提示词

````text
请基于已经确认的用户故事和 P0—P2 优先级，和我一起梳理产品功能及页面结构，等我确认后写入产品事实文档。本轮产物是功能清单、页面结构和关键使用路径。

以下路径均相对于项目根目录，`docs/` 与源码仓库 `src/` 同级。

### 1. 读取已确认的需求

先读取根目录的 `AGENTS.md`，按其中的文档入口查阅产品目标、用户角色、用户故事及优先级，以及已有的功能和页面结构文档。

简要说明本轮已经确认的建设范围，沿用已有故事编号和优先级。信息不足时，先提出需要我决定的问题，等我回答后继续。讨论中出现的新需求先列为候选，由我决定是否补充或调整用户故事，再纳入功能规划。

### 2. 一起梳理产品功能

先讨论 P0 故事需要的功能，再讨论 P1、P2 对应的功能，按照已经确认的范围区分本轮需要与后续保留的部分。

每轮围绕一组相关故事展开，提出功能建议，说明每项功能对应哪些故事、帮助用户完成什么，以及关键行为和完成结果。把职责相近的功能归为一组，与我讨论哪些需要合并或拆分。我确认这一组功能后，再继续下一组。

### 3. 一起梳理页面结构

基于已经确认的功能清单，提出页面安排，与我逐项讨论：

- 页面名称、使用角色和主要职责。
- 页面包含哪些主要信息和操作，分别对应哪些功能。
- 用户从哪里进入，完成操作后前往哪里。

依据实际使用过程决定页面如何划分：同一页面可以承载多个功能，同一故事也可以跨越多个页面。涉及角色权限差异或影响任务完成的特殊情况时，与我确认页面如何呈现，以及用户如何继续操作。

用页面层级说明导航结构，用"入口 → 页面 → 操作 → 后续页面或完成结果"说明关键使用路径。逐条检查本轮范围内的故事是否有对应的功能和页面支持，尤其确认 P0 故事能够从开始使用一直完成目标。发现缺少的功能、入口或步骤时，提出具体问题与我讨论，等我确认处理方式后继续。

### 4. 确认结果并写入事实文档

汇总功能清单、页面结构和关键使用路径，明确它们与用户故事的关联，单独列出仍待决定的问题。等我明确确认本轮结果后再写入。

写入时，分别检查 `docs/facts/` 中是否已有负责功能清单和页面结构的文档：已有则更新原文件；尚无对应文档时，功能清单保存到 `docs/facts/product-functions.md`，页面结构和关键使用路径保存到 `docs/facts/page-structure.md`。

仅写入我确认的结论，保留原文档中本轮范围外且仍然有效的内容。用户故事与优先级通过故事编号引用原文档，页面通过功能名称或已有编号引用功能清单，每类信息在其责任文档中维护。

完成后回读文件，核对功能、页面、关键路径及故事关联与确认结果一致，确认文档之间的引用有效。向我说明实际更新的文件路径和本轮确认的范围，然后等待下一步指令。
````

## 04 技术方案提示词

````text
请基于已经确认的用户故事、优先级、产品功能和页面结构，和我一起讨论技术选型与整体架构。如果需要数据库，也要完成数据结构设计。等我确认后，将结论写入产品事实文档。本轮产物是设计文档，具体开发任务随后再安排。

以下路径均相对于项目根目录，`docs/` 与源码仓库 `src/` 同级。

### 1. 读取产品事实与实际项目情况

先读取根目录的 `AGENTS.md`，按其中的文档入口查阅已确认的产品事实、工程规则和已有技术方案。已有源码时，检查 `src/` 中与本轮方案有关的依赖和目录结构，区分实际实现、已确认方案和尚待讨论的建议。

简要说明本轮需要支持的功能和关键使用路径，以及已有技术限制。缺少会影响选型的信息时，围绕部署环境、预算、使用规模或我的技术经验等实际问题提问，等我回答后继续。已有结论直接沿用。

### 2. 一起讨论技术选型

先讨论哪些数据需要保存、如何查询和共享，与我确认是否需要数据库。随后围绕实际需要的技术逐项讨论，包括应用使用的语言与框架、数据存储方式，以及确有需要的外部服务。

每项关键选型先给出推荐方案，说明它满足哪些已确认需求、开发和维护的难度、运行成本及与其他技术的配合方式。存在值得比较的备选时，用我能理解的语言说明主要差别，帮助我决定。涉及版本兼容、维护状态或费用等会变化的信息时，查阅官方资料核实，并附来源。

方案的复杂程度以已确认的建设范围和使用规模为依据。每轮集中讨论一个关键决定，我确认后再继续下一项。需要数据库时，在这一阶段一起确认采用哪种数据库。

### 3. 一起确定整体架构

基于已确认的选型，提出整体架构，用简明结构图说明系统由哪些部分组成、各自负责什么、如何通信，以及数据在哪里保存。说明 `src/` 内的主要职责划分。

结合核心用户故事，说明从页面操作、业务处理到结果返回的过程；涉及数据保存或外部服务时，将相应的读写与调用过程说明清楚。涉及身份权限或敏感数据时，明确访问控制、数据保护和失败处理由哪个部分负责。

检查本轮各项功能是否都有明确的技术责任，尤其确认 P0 故事的关键使用路径能够完成。发现缺少的能力或与产品事实冲突的地方时，提出具体问题，与我确认处理方式。我确认整体架构后，再继续完善所需的数据结构。

### 4. 需要数据库时，设计数据结构

已确认无需数据库时，将采用的数据保存方式和理由加入方案汇总，进入第 5 步。

需要数据库时，先梳理需要保存的数据对象及其关系，说明对应的功能。采用表结构时，逐项与我讨论：

- 每张表的用途，以及字段名称、数据类型、是否必填、默认值、主键和唯一约束。
- 表之间的关联方式、必要的外键，以及关联数据更新或删除时如何处理。
- 根据实际查询和更新方式，需要哪些索引，以及哪些关联更新必须一起成功或失败。

采用其他数据模型时，用相应的数据结构、标识和关联规则表达设计。外部服务负责保存的数据明确其归属，本项目的数据结构只保存自己负责的信息。

用字段说明和关系图展示设计，检查其是否支持已确认的功能及关键使用路径。业务含义和规则引用原产品事实，具体存储结构在数据库设计文档中维护。

### 5. 确认结果并写入事实文档

汇总技术选型及理由、整体架构、关键数据流，以及需要时的数据库设计。明确仍待决定或验证的问题，等我明确确认本轮结果后再写入。

分别检查 `docs/facts/` 中是否已有负责技术方案和数据库设计的文档：已有则更新原文件；尚无对应文档时，技术方案保存到 `docs/facts/technical-solution.md`，需要数据库时，数据结构保存到 `docs/facts/database-schema.md`。

仅写入我确认的结论，保留本轮范围外仍然有效的内容。产品需求引用原事实文档和故事编号；如有数据库设计，技术方案通过链接引用。每类信息在其责任文档中维护。

完成后回读文件，核对选型、架构、数据结构和文档引用与确认结果一致。向我说明实际更新的文件路径、本轮确认的范围和尚未验证的问题，随后等待我安排具体开发任务。
````

## 05 开发里程碑提示词

````text
请基于已经确认的用户故事、优先级、产品功能和技术方案，和我一起确定开发顺序，以及每个开发里程碑的目标、范围和完成条件。等我确认后保存计划，具体开发任务随后再安排。

以下路径均相对于项目根目录，`docs/` 与源码仓库 `src/` 同级。

### 1. 读取事实并确认规划范围

先读取根目录的 `AGENTS.md`，按其中的文档入口查阅已确认的用户故事及优先级、功能清单、技术方案和工程规则。需要理解具体使用过程或数据依赖时，再查阅对应的页面结构和数据库设计。

已有里程碑计划或开发成果时，读取相关计划、实现和验收记录，区分已完成、待验证和待开发的内容。

简要说明当前已经确认的建设范围、已有进度和重要依赖。缺少会影响规划的信息时，先向我确认本轮希望做到什么程度，以及需要优先实现或验证的使用场景，等我回答后继续。已有结论直接沿用。

### 2. 一起确定开发顺序

以 P0 核心故事和已确认的建设范围为依据，结合功能与技术依赖，提出建议顺序，并解释为什么这样安排。P1、P2 按其优先级和实际依赖安排到适合的阶段，区分本轮范围与后续候选。

优先让用户能够完成一项核心任务，再逐步扩充能力。必要的技术准备应说明它支持哪个近期目标，安排到对应阶段。已有记录指出某项关键技术尚未验证、可能影响后续开发时，提出针对性的验证安排，与我讨论它应放在哪个阶段，以及验证结果如何影响后续计划。

发现优先级、技术依赖或当前范围之间存在冲突时，指出具体影响，让我决定取舍。我确认主要开发顺序后，再细化各个里程碑。

### 3. 一起明确每个里程碑

按照能够单独演示和验证的阶段成果划分里程碑，数量和大小由实际目标与依赖决定。使用稳定编号，例如 `M1`、`M2`；沿用已有编号。

每个里程碑需要与我讨论清楚：

- **阶段目标**：完成后，用户能够完成哪些事情，或者哪项必要能力得到验证。
- **包含范围**：对应哪些用户故事和功能，通过已有编号或名称引用原文档。
- **前置条件**：依赖哪些里程碑、技术准备或外部条件，满足什么条件后可以开始。
- **交付结果**：实际要交付哪些功能、页面、数据能力或其他必要产物。
- **完成条件**：用哪些具体操作和预期结果判断目标已经达到，并按工程规则安排相应检查与验收。

每轮围绕一个或一组相关里程碑讨论，由我调整目标、范围或拆分方式，确认后再继续。涉及时间安排时，依据我提供的人员、可投入时间和期限讨论，明确估算所依赖的条件。

### 4. 确认整份计划并保存

按开发顺序汇总里程碑及其依赖，检查本轮范围内的故事是否都有安排、前置条件是否能按顺序满足、完成条件是否可以实际检查。后续候选和仍待决定的问题单独列出，等我明确确认整份计划后再保存。

优先更新项目已有的里程碑计划；没有对应文档时，创建 `docs/Spec/milestones.md`。保存我确认的顺序、目标、范围、依赖、交付结果和完成条件，保留本轮范围外仍然有效的内容。

完成后回读计划，核对开发顺序、故事关联、依赖和完成条件与确认结果一致，确认文档引用有效。向我说明文件路径、本轮确认的范围和待解决问题，然后等待我指定下一步工作。
````

## 七、配套方法论要点

- **推荐推进顺序**：项目建设 → 用户故事与优先级 → 产品功能与页面结构 → 技术方案 → 开发里程碑；每个功能都应能追溯到它服务的用户故事
- **用户故事三要素**：什么场景、想完成什么、怎样算完成（为什么来、先看到什么、接下来要做什么）
- **优先级定义**：P0=当前版本必须满足，缺少它核心目标或主要使用流程无法成立；P1=能明显改善主要使用体验，但缺少它仍能完成核心流程；P2=改善细节或满足较少使用的场景，当前阶段可以推后
- **角色原则**：新增角色作为建议由人决定是否纳入；按当前需要选择角色，每多一个角色功能更复杂一分
- **里程碑五要素**：阶段目标 / 包含范围 / 前置条件 / 交付结果 / 完成条件；里程碑要能单独演示和验证，稳定编号 M1、M2
- **目录规范**：`docs/facts/` 责任文档制（user-stories.md、product-functions.md、page-structure.md、technical-solution.md、database-schema.md 等）+ `docs/Spec/`（含 milestones.md）+ `docs/工程规则.md` + `AGENTS.md` + `README.md` + `src/`（独立 Git 仓库，main 主分支）
- **核心纪律**：同一事实只在一个位置维护；AI 建议与已确认结论明确区分；等我明确确认后再写入、仅写入确认结论；开发与验收使用同一份 SPEC；独立任务分支开发、按授权合并回 main、上线需明确确认；完成后回读文件逐条核对
